## Scope

This is an explicit `camera-test` firmware environment, separate from `network-test` and the disabled default starter. It initializes the built-in camera and continues station s11 camera heartbeats. It does not initialize external sensors, servos or the flash LED, select mechanism pins or angles, or move hardware. Camera LEDC timer/channel configuration is only for the onboard camera clock.

The monitor continues running its network-test firmware, with all fill values labelled simulated. The hardware LAN Compose setup from [hardware-test.md](hardware-test.md) must be active. Backend inference must remain explicitly `mock` for this stage. The camera checks `/api/summary` before each upload and refuses to upload if the provider is not mock; no Roboflow key is embedded or used.

Mock decisions depend on the scripted scenario, not the image contents. This test proves capture and image transport; it does not measure waste-classification accuracy.

## Build and upload

Private credentials remain in ignored `include/config.local.h`, generated by `scripts/configure-hardware.py`. Preserve the complete original flash backup before upload; an existing verified backup need not be repeated.

```sh
uv tool run --from platformio pio run -d firmware/esp32-cam -e camera-test
uv tool run --from platformio pio run -d firmware/esp32-cam -e camera-test -t upload \
  --upload-port /dev/serial/by-id/usb-1a86_USB_Serial-if00-port0
```

Serial output at 115200 baud should include a successful camera initialization with the detected sensor PID, Wi-Fi address, backend readiness 200 and MQTT connection. Wi-Fi connects before camera initialization, and the HTTP server binds only after the network stack is ready. With PSRAM it captures VGA (640×480) JPEGs; without PSRAM it uses QVGA (320×240). It uses one framebuffer, performs a few startup warm-up exposures and does not upload on a timer. Camera initialization failure leaves heartbeat diagnostics available, with capture endpoints returning an explicit error.

## Manual endpoints on the camera

Use the actual camera IP printed in serial logs (the initial test address was `192.168.1.190`; DHCP may change it):

| Method / camera path | Action |
| --- | --- |
| GET /status | Sensor PID, camera readiness, PSRAM, latest event metadata and disabled actuator state |
| GET /capture | Capture and return a fresh JPEG; no backend classification |
| POST /classify | Capture a fresh JPEG and upload it to backend multipart `/api/classify` using mock scenario `plastic` |

These are local diagnostic endpoints without authentication; keep them on the trusted LAN. They provide no actuator or remote motor commands. The browser can display `http://CAMERA_IP/capture`; refresh deliberately for another exposure. Responses use `Cache-Control: no-store`. No JPEG is written to persistent storage on the device or backend in the default configuration.

The preview uses the framework’s binary-response writer; the image upload streams the multipart fields and framebuffer without allocating a second image-sized buffer. Up to three bounded upload attempts reuse the identical JPEG, request UUID, station/device IDs and scenario. HTTP 200 returns the persisted event. Transport/provider failure never causes a completed-sorting report. The test route is synchronous; heartbeats can pause during bounded HTTP requests. This diagnostic mode is not a production asynchronous camera pipeline.

After a successful prediction, the board separately publishes an actual `disabled` actuation outcome with `simulated: false`: the physical board did not move anything. It waits two seconds after the response to reduce clock-order issues; NTP synchronization is required. MQTT acknowledgement alone is not proof of database persistence; verify through the API. The status endpoint calls this acknowledgement `disabled_outcome_broker_ack` explicitly.

## Verify the full path

From backend/:

```sh
uv run python ../scripts/verify-camera.py --camera-host CAMERA_IP
# Optionally retain a private local preview for image inspection:
uv run python ../scripts/verify-camera.py --camera-host CAMERA_IP \
  --save-preview ../.hardware-backups/camera-preview.jpg
```

The verifier checks camera readiness, downloads and fully decodes a real JPEG, requests a separate captured-image classification, checks the initial outcome is null, then waits for the matching disabled outcome to persist through MQTT. It never saves an image unless `--save-preview` is passed. The preview and classified exposure are separate captures and may differ if the scene moves. The backend continues to discard uploaded image bytes by default.

## USB serial reset behaviour on Linux

Opening a serial tool may pulse the baseboard's reset lines. Avoid opening other tools on the camera UART while an HTTP capture/classification check is running. The PlatformIO environments configure monitor DTR/RTS to zero. If the board is held in reset when a monitor closes, Espressif documents disabling Linux hang-up-on-close:

```sh
stty -F /dev/serial/by-id/usb-1a86_USB_Serial-if00-port0 -hupcl
```

This setting can reset when USB is unplugged. See [Espressif boot/reset guidance](https://docs.espressif.com/projects/esptool/en/latest/esp32/advanced-topics/boot-mode-selection.html). Initial Wi-Fi association may retry before it succeeds; diagnostic disconnect reason codes are logged without printing credentials.
